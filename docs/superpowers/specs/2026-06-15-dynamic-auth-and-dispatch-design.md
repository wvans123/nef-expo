# AF 接入认证、场景授权与调用回执设计

分类：架构 / 安全设计。更新：2026-09-22。
状态：5G 参考已核对；精简回执与证据标注已实现；新场景接口已实施独立订阅授权；标准安全接入、资源级场景策略与 6G 扩展仍未实施。此文件是认证 / 授权设计的唯一维护说明；接口契约见 [接口对接参考](../../reference/integration.md)。

## 本轮访问边界补充

三个场景均支持 Intent，仍按所选场景校验订阅；端网协同的 API / Tool 权限不因此合并成无限制的资源权限。

场景购买时勾选的子能力同步获得独立 API / MCP 权益，以 `scene:<id>` 记录来源；未选能力不扩权，显式空选择只开通场景入口。基础调用、MCP 发现、订阅查询使用同一权益并集。撤回场景只移除该来源，保留其他场景、旧套餐、单订或等级覆盖；所选能力不重复收取单项月费。旧能力套餐与新场景入口仍保持分离，不因同名或共享子能力而开通别的场景服务。

演示用 `GET /api/v1/integration/subscriptions?account_id=1` 以精确账号名查询，**不要求 NEF 账号 Key**；旧公网入口仍依赖 Cloudflare Access。共享入口内可查其他约定编号，不是生产租户隔离。1.1 purchased_packages 汇总已开通场景与旧套餐，草稿不算已购；不返回密钥或授予执行权。本轮还增加无 Key 场景回传和开放 MCP 一步登记，适用于获准测试网络；执行与网络代理仍独立鉴权。契约见[订阅查询](../../reference/subscription-query.md)和[农场联调](../../reference/farm-integration.md)。

私有 MCP 登记、发现与发布需 `af:register`；无 Key `/api/v1/af/mcp-servers` 使用配置的 open_registration_account 并标记 open。开放登记跨账号可见，带 af:register 的账号可操作；私有登记、目录快照和套餐仍隔离，套餐定义管理需 pipeline:manage。服务连接默认需精确允许列表，显式 allow_unlisted_mcp_servers 会放宽目标地址，存在内网探测风险。AF Key 不发送给上游；登记、发布均不自动产生执行授权。

## 1. 先定授权责任，而不是先定动画

本项目建议采用“NEF 开放平台统一提供场景入口”的产品定位，但逻辑上分开：北向开放 / 授权层、网络侧场景执行方、底层网络能力。机器狗巡检、车流量检测、端网协同追踪是本项目的场景服务，不应称为 5G 标准已经定义的 NEF 场景 API。该责任分工仍需与内部服务提供方确认。

- 如果场景服务由本平台对 AF 提供，本平台在入口落实场景服务的授权；内部执行方仍落实设备、区域、数据等实际资源权限。
- 如果场景服务实际上由外部业务平台提供，场景授权属于该提供方，NEF 负责其中暴露的网络能力授权。不能只因为请求途经 NEF，就把整个业务所有权与所有授权都归给标准 NEF 网元。
- 订阅是商业权益的来源之一；认证、服务授权、资源授权是不同判定。买了套餐、持有有效凭证，都不代表可以调用任意资源。

外部消费者使用自己的 NEF Key 订阅第三方 MCP 工具，经 `/mcp` 或兼容 tools/call 入口调用时校验 mcp:tools、逐工具订阅、发布状态、URL 许可和 inputSchema。PRO/MAX 与发布者身份不授予隐式权益；下架或取消订阅拒绝后续调用。此流程不复用下面的内部 network_clients 授权。

内部网元调用 AF 工具使用独立 `network_clients` 身份与显式 `af_accounts` 范围；不复用 AF Key。入口为 `/api/v1/network/af-servers/{id}/mcp`，每次核验身份、账号范围、上游允许列表、工具发现状态及输入 schema；任一失败不外发调用。NEF → AF、NEF → TRF 的服务端凭证分开配置。2026-09-21 新 TRF 契约发布填写的 AF 原始 MCP 地址，直连由对方控制认证；这里的 NEF 代理鉴权只适用于独立 gateway_path，不覆盖绕过 NEF 的直接调用。旧代理登记格式仅保留兼容。该入口不使用北向场景订阅判定替代网络调用授权。详见[展示与网络对接设计](2026-06-11-frontend-demo-redesign-design.md#42-网络内部怎样调用)。

## 2. 5G 参考基线（不是 UE 入网认证）

本期参考的是 AF–NEF 应用接入，而不是让 AF 运行终端入网的 5G-AKA。

已核对 [TS 33.501 V17.15.0](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/17.15.00_60/ts_133501v171500p.pdf)，§5.9.2.3、§12.1–12.5：NEF 需判定 AF 的请求授权；运营商域外 AF 的通常路径规定基于证书的 TLS 双向认证与接口保护，§12.4 规定 OAuth 授权；支持 CAPIF 时按 §12.5 采用其安全方法选择。不能把单个本地 Bearer API Key 当成已完成这套机制。

已核对 [TS 33.122 V19.3.0](https://www.etsi.org/deliver/etsi_ts/133100_133199/133122/19.03.00_60/ts_133122v190300p.pdf)，§6.5.2.3：在 CAPIF 的 TLS + OAuth 方法下，CCF 是授权服务器，API Invoker 是客户端，AEF 是资源服务器；AEF 核验令牌及其调用权限。CAPIF 不只有这一种安全方法，不能把一种流程当成所有部署的固定拓扑。

同规范 §6.12 已支持细到服务、服务操作和资源的授权。因此“按场景及资源授权”并非必然要等 6G，也不能宣称这些粒度是 6G 独有创新。巡检场景的服务标识、操作及业务资源映射仍需由本项目定义，规范没有替我们定义机器人业务契约。

## 3. 场景如何授权（待实现设计）

授权对象建议为：**AF 主体 × 场景服务 × 操作 × 资源集合 × 约束**，不是中文场景名或 PRO 标签。

示例策略（仅说明业务含义，不是已有接口字段或标准 scope 字符串）：某 AF 可发起 robot_patrol，仅限园区 A、指定机器人 / 数据源，在授权时间窗内执行；不能因为订阅巡检而使用园区 B 的摄像头。

三个场景的重点：

- 机器狗巡检：场景调用权 + 允许的园区、机器人、数据源及时间范围。
- 车流量检测：场景调用权 + 路口 / 路段、统计时间窗、允许返回的数据类别。
- 端网协同识别追踪：服务操作权 + 终端、输入图像 / 视频源、目标与结果范围。停止 / 更新等操作只有内部实际支持后才定义。

如果 AF 已选定场景，携带明确场景上下文可在 NEF 开放层先检查对应策略，再转发原文。若只发自由文本，NEF 只能先做入口准入；内部 NW Agent 或服务路由方识别出具体服务、资源后，必须在执行前落实授权，不能把“intent:submit 通过”视为整个计划获批。旧全局 text-only 接口并没有实现后面这道场景策略绑定；新 `/services/{service_id}/intent` 已在接入时绑定具体服务订阅，但仍不解析 / 授权意图中的任意资源。

推荐职责：运营商 / 服务提供方管理授权策略；NEF 开放层校验并执行入口策略；执行方负责将授权范围绑定到具体执行与结果。授权上下文必须来自可信主体并防篡改，不能只相信请求里的 af_id / service_id 文本。内部使用服务凭证调用不应扩大 AF 原始权限，也不建议将北向令牌无条件透传为所有内部服务的通用凭证。

生产场景回传仍需独立校验写入方、读取方和资源范围。当前测试实现的 `/api/v1/scene-feedback/{scene_id}` 无 Key 可写可读，三场景 owner=None、全账号共享，不具备数据来源认证或租户隔离。旧 `/api/v1/scene-feedback` 仍根据专用 Key 哈希路由，正文不能改目标；general 与手工通道保持私有。无论采用哪种入口，都不代表已获得设备 / 人员数据的业务授权。

## 4. 调用界面如何显示

回传窗口只在具体调用区显示文字和结构化数据，媒体仅后端接收；能力超市、我的订阅不显示或轮询回传窗。`?ops=1` 仅控制回传资料和通知诊断显示，不是管理权限。

调用时只展示紧凑回执：**AF 身份 / 入口权限 / 场景授权（基础能力入口为能力使用权）**。绿色来自后端对应检查证据，拒绝显式标注，无回执保持待核验。资源策略未实现，不将它列为已通过控制，具体限制放访问策略的折叠实现说明；不因 HTTP 200 / 503 或动画计时推断授权成功。

身份、scope、权益都已经通过但内部接口未配置 / 超时时，错误响应保留实际完成的 nef_auth 回执，区分“准入通过”与“业务转发失败”。旧全局 Intent 仍只校验入口资格；新场景 Intent 回执明确绑定所选服务的订阅授权，资源级策略仍未实施。

页面使用“可信接入 · 统一身份 · 按场景授权”等产品表达。5G 参考、API Key 实现及资源控制限制放访问策略详情，不再把“5G 参考与边界”作为展示按钮。场景演示 / 真实调用的数据来源标识独立保留。

## 5. 当前实现与未实现

已实现：本地 API Key 存在性检查、入口 scope、原有订阅 / 等级判定及新场景服务的独立订阅授权；后端回执与界面一致解释；错误路径保留已完成的准入证据。

未实现：正式 AF 证书 / mTLS、OAuth/JWT 令牌核验、有效期 / 独立撤销列表、资源级场景策略、持久审计。当前生成 request_id 不等于已落审计日志；历史随机步骤耗时仍是旧工作台的演示数据，新回执不呈现这些耗时。

不改变现有账号模型，不为了把图标点绿而配置虚假的 CCF/NRF 或证书。本次没有部署新身份服务、修改用户凭证或声称标准符合性通过。

## 6. 6G / Agent / Intent 扩展的考虑（设计候选）

在既有安全接入之上，需要进一步明确 Agent 代表哪个 AF / 用户、可委托到什么范围、自然语言目标解析成哪些操作、运行中目标变化是否需要重新授权、撤销后后续步骤如何停止。它们是本项目值得补齐的执行授权问题，不在此声称是已定稿的 6G 标准，也不把 5G/CAPIF 已有的资源粒度授权改名为 6G 创新。

新场景入口已按服务 ID 与允许模式绑定订阅；下一步确认场景提供方与最小资源约束，再扩展可信资源策略；正式 mTLS / OAuth 采用实际部署方的身份体系接入，不另造一套演示协议。

## 历史记录：2026-06-15 动态鉴权与路由草案

以下保留用于回溯。其“七级全绿”“未过期、未吊销”“审计落账”等演示口径不代表当前已实现，且不能作为 5G / CAPIF 符合性证据。当前判定以上文为准。

## 背景与目标

现状两处不足，演示时撑不起"流程感"与"可信度"：

1. **鉴权太静态**：`_auth_evidence` 把四步检查全写死成 `passed`，前端只是四个打勾的卡片，像一张结果截图，不像 NEF 在"逐级鉴权"。
2. **粒度错配 + 无后台实现**：NEF 目录是 tool 粒度，但同事的后台只实现到场景/套餐级，单个 tool 在我们后台没有真实代码。核心疑问是——*若 NEF 把一个 tool 级请求转给后台，后台分得清这是要它干嘛吗？*

目标：把鉴权做成**动态、逐级、客户看得见**的 CAPIF 流水线；并用**显式请求信封 + NEF 分发表**讲清"后台分得清、没实现的由 NEF 兜底"。

## 一、CAPIF 实时鉴权流水线

基于 3GPP CAPIF（AEF 对 API Invoker 逐次鉴权）建模为 7 级流水线。后端按真实条件计算每级 `status`，前端逐级点亮动画（每级 ~120–260ms + ✓/⚠），让客户"看见"。

| 序 | code | 标签 | 动态判定 |
|---|---|---|---|
| ① | access | 接入·限流 | TLS/接入点；配额 used/limit（演示恒过，展示配额计数） |
| ② | credential | 凭证解析 | Bearer 头存在且格式正确 |
| ③ | token | 令牌校验 | 签名/有效期/未吊销（演示恒过） |
| ④ | invoker | 身份识别 | API Key → AF 账号（CAPIF API Invoker ID） |
| ⑤ | scope | 权限范围 | required_scope ∈ key.scopes |
| ⑥ | authz | 授权判定 | `_entitled`：订阅 ∪ 等级 ∪ 第三方；不满足 → 拒（402） |
| ⑦ | audit | 审计落账 | 写 request_id（无论放行/拒绝都落账） |

**分支（动态可感知的关键）**：
- 全部通过 → decision=`allow`，七级全绿。
- 未授权且未确认支付 → ⑥ 变橙 `denied`、⑦ 仍落账 `审计:拒绝`，HTTP 402，前端把流水线渲染到 ⑥ 再弹支付卡。
- 缺/错 Key → ② `denied`，HTTP 401（前端基于固定模板渲染到 ②）。

**数据结构**：`_capif_pipeline(key, rec, cap, scope, *, entitled, paid) -> {request_id, decision, quota:{used,limit}, stages:[{seq,code,label,status,latency_ms,detail}]}`。
放行结果挂在 `result["nef_auth"]`（在原 stamp 基础上增补 `pipeline`/`quota`/`dispatch`，保持原字段不删，兼容老测试）；402 时挂在 `_payment_required_payload` 的 `pipeline` 字段。

## 二、路由判定 + NEF 分发表

**显式请求信封**（NEF 转后台时携带，后台靠 `service_id` 分发，无歧义）：
```json
{ "request_id":"req_…", "service_id":"robot_patrol", "tool_id":"target_detection", "params":{…} }
```

**NEF 分发表**：每个暴露能力 → 落地目标二选一。
- `BACKEND_SERVICES`（演示初值）：`{robot_patrol, traffic_forecast_pkg, uav_track}`——后台真实现的场景级 service_id。
- 单个 tool / 未注册场景 → `nef-ref`（NEF 参考回显，前端标注 mock）。

`_dispatch(kind, id) -> {target:"backend"|"nef-ref", service_id, envelope, note}`：
- 场景 id ∈ BACKEND_SERVICES → `backend`，note="命中后台 service_id"；
- 否则 → `nef-ref`，note="无后台实现 → NEF 参考回显"。

**后台分得清的保证**：NEF 只把 BACKEND_SERVICES 里（后台声明过的）id 转发出去；没实现的 tool 级请求根本不出向，由 NEF 参考回显兜底。歧义在 NEF 这层消化。

新增 `GET /api/v1/dispatch-table` 返回全表，前端在「场景方案」页渲染一张可视分发表。

## 三、贯穿四个入口

同一条流水线 + 路由判定出现在：API 直调、MCP tools/call、意图受理、场景运行。
- API/MCP 单 tool：流水线 → 路由=nef-ref → 结果信封（标 mock）。
- 场景运行：流水线 → 路由=backend(service_id) → 展示转发信封 → 回执轨迹。
- 意图：受理流水线沿用 `_auth_evidence` 升级为同结构 stages。

## 四、改名

`场景蓝图` → **`场景方案`**（tab 按钮 + 区标题 + playbook/README 引用）。运营商一听即懂：每个场景的成套解决方案 + 怎么调 + 一键跑。

## 五、前端

- 复用组件 `renderAuthPipeline(el, pipeline, onDone)`：逐级点亮动画 + 路由判定行。
- API 直调：调用即播放流水线 → 路由 → 结果信封；402 播放到 ⑥ + 支付卡。

## 六、测试

首页 TRF 登记与调用授权分开：`/api/v1/network/trf/catalog` 仅公开去掉 URL/凭据的目录缓存；刷新上游、发布、撤回由 NEF 实例执行，要求任一有效 NEF Key，但不要求 `af:register`，状态不按 AF 账号分区。三分类 MCP 的公开 `tools/list` 不要求 Key，`tools/call` 仍要求 `mcp:tools`、订阅及 live 调用检查；登记不会授予权益，通知不会执行工具。TRF 读取模式只展示服务描述，不转成可调用工具。

- `nef_auth.pipeline` 七级、decision=allow（已授权调用）。
- 402 payload 含 pipeline 且 ⑥ authz=denied。
- `/api/v1/dispatch-table`：tool→nef-ref，featured 场景→backend。
- 场景运行回执含 dispatch.target=backend + envelope.service_id。
- 全量回归（39 测试）保持绿。

## 原子能力身份命名复核（2026-09-10）

`identity_service` 展示名改为“应用接入身份”，不再声称为任意 AF/Agent 颁发 AKMA 网络身份。TS 33.535 V18.8.0 中 AKMA 涉及 UE 主认证后的 UE-AF 应用密钥上下文；CAPIF Invoker 接入管理与该机制不能合并成泛化的 Agent 发证能力。本地账号 Key 仍是演示平台凭证。逐原子能力与证据基线统一见 [README 能力标准复核](../../../README.md#六能力目录与标准复核)。智能编排只要求套餐管理 scope，推荐不授予订阅、资源权限或发布权限；执行时仍需相应调用授权。
